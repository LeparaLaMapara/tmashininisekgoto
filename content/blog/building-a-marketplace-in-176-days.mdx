# Where the System Says No: AI Engineering on a Live Marketplace

*Part one of two. This one is the AI layer and the process around it. [Part two](/blog/the-platform-is-a-design-input) is the infrastructure, the security boundary and the data.*

---

## The morning the assistant started lying about itself

On 29 August my customer facing assistant began returning 404 on every message.

The cause took two minutes to find. Months earlier I had written a model id into a source file. The provider retired that model. My code kept asking for it.

I want to be precise about what failed there, because the obvious reading is wrong. The abstraction was fine. Every provider sat behind an interface, every call went through one gateway, and swapping Anthropic for OpenAI was a single environment variable. None of that helped, because the thing that broke was not the provider. It was a **model id sitting in code as a constant, with nothing anywhere in the system able to refuse it.**

I had written a rule down. Nothing enforced it.

That is the pattern I found everywhere once I started looking, and it is the closest thing I have to a design philosophy after six months:

> A design is only real where something refuses. Everywhere else it is only described. Almost every defect I found in six months was in a place where I had written the rule down and nothing enforced it.

ThabangVision is a booking and equipment rental platform for South African filmmakers and photographers. I built it alone, with agents, between March and August 2026. Here is the honest shape of it.

| Measure | Value |
| --- | --- |
| Commits on `main` | 257 |
| Days, first commit to last | 176 |
| Lines of TypeScript and TSX | 69,622 across 417 files |
| API routes | 95 |
| SQL migrations | 61 files, numbered to 058 |
| Unit assertions | 300 passing |
| Browser test blocks | 114 across six specs |
| Runtime AI agents | 7 |
| Authors | 1 |
| Equipment bookings when I last audited it | 7 |

That last row matters. This is a live system taking real payments, and it is also early. Every number above is more useful to you if you know which stage it describes, and a post that quietly omits the volume while quoting the line count is selling you something.

## The registry that refuses a model

The fix for the 404 was not to update the id. It was to notice that **a gateway's models are data, not code.**

Before, the gateway was a switch over three hardcoded ids. Adding a model, changing which one ran, or pointing at something local all meant editing a source file and deploying. After, every model is a row in a registry, and every id is overridable by environment variable.

The interesting part is not the registry. It is what I chose to record about each model, because each field exists so the system can refuse something.

| Field | What it holds | What it lets the system refuse |
| --- | --- | --- |
| `provider` | anthropic, openai, google, groq, or local | Nothing on its own. This is the part I already had. |
| `modelId` | The provider's id, overridable by env | A retired id becomes a config change, not a deploy |
| `tier` | smart or fast | An expensive model on a trivial query |
| `openWeight` | Whether the weights are published | A proprietary model, unless explicitly opted in |
| `tools` | Whether it reliably does tool calling | A model that cannot serve the assistant |

Three of those five are worth more than they look.

**`local` is a first class provider, not a stub.** Ollama, vLLM, LM Studio and any private gateway all speak the OpenAI wire format. So the OpenAI adapter pointed at a different base URL reaches every one of them with no new dependency. Running a model on my own hardware became one environment variable rather than a project.

**`tools` is a property I measure, not one I assume.** My assistant passes tools on every single turn, so a model that cannot reliably call them must never serve it. When I moved the assistant to Qwen, the commits read in this order: prove tool calling, then flip. The gate found two real bugs before the switch went anywhere near a customer.

**`openWeight` marks the weights, not the price.** An open weight model called through a hosted API still bills you. Only self hosting is actually free. I wrote that distinction into the field's comment because it gets fudged constantly and I did not want to fudge it in my own cost model.

### Failing over, and where I deliberately stopped

Calls that do not stream now fail over across providers on a retryable error, with each attempt bounded by a timeout so one hung provider cannot hold a serverless function open until its ceiling.

Streaming does not fail over in the middle of a stream. That is deliberate. Doing it means either buffering the first token, which costs you the reason you streamed, or replaying a half sent response, which is worse. The streaming path fails over before the first token, then commits.

I did the non streaming path first, and the reason is the sort of thing you only learn by operating something rather than designing it. Those are the admin drafting routes, the ratecard import, the WhatsApp integration. **Nobody is watching them.** A silent failure there sits for days. A failure in the chat window gets reported in minutes, by the customer, for free.

## An alert is not a control

Every model call in the agent runtime goes through one function that writes a row with the agent, provider, model, user and token counts. That gave me perfect visibility into spend.

For four months, visibility was all I had. The only guard was a cron job that emailed me at eighty percent and one hundred percent of budget.

That is not a limit. Between two runs of that job, my spend was uncapped. A runaway loop, or somebody rotating addresses past my per minute cap, could have driven the bill arbitrarily high and I would have found out at noon the next day.

So I replaced it with a gate that reads month to date spend and refuses the call. The comment I left on it is the shortest version of this whole post:

> An alert is not a control. This is the control.

What I like about that module now is not the gate. It is that I wrote down why it is imprecise on purpose. It caches the monthly total briefly per instance, and optimistically adds each allowed request's own estimate to the cached figure so the number trends upward between refreshes instead of sitting stale. Overshoot is bounded by concurrent instances times one request, which against a monthly rand cap is nothing.

I could have built a precise counter shared across every instance. I deliberately did not, and said so in the file: for a monthly budget backstop that is over engineering. **Knowing which problem does not deserve the correct solution is most of the job.**

There is one more piece of paranoia in the pricing table, and it is the one I would port to any system that spends money automatically. Models I know are free are listed explicitly. Anything not in the price table and not in that list is charged at the **worst known rate**, with a floor. Unknown must never default to free, because the failure mode of the opposite default is an unbounded bill from a model somebody forgot to register.

## The function that cannot reach the database

Underneath the AI work sits ordinary software engineering, and one rule carried more weight than the rest: **the decisions live in modules that cannot reach the network.**

Availability, cart pricing, delivery quoting, booking validation, ranking, and the consistency checks are all pure. Each takes data in and returns a decision. The database call lives somewhere else entirely.

That is why 300 unit assertions run in under half a second with no database, no network and no API key. Every genuinely hard rule in the product, unit aware availability, expiring checkout holds, bulk discounts, cancellation windows, distance priced delivery, is covered by a test that runs faster than I can read the output.

It is also the rule that cost me nothing. Six months of log and I cannot find a bill for it.

Two other things in this layer are worth stealing. Money is stored as integer rand cents, never a float. And the schema has two different booking types that must never be conflated:

| | Service booking | Equipment booking |
| --- | --- | --- |
| Unit | Time. A shoot. | Dates. A rental period. |
| Money out | Creator payout | Deposit released on return |
| State after payment | `paid` | `confirmed` |

That last row cost me an afternoon. My first consistency checker treated both with one vocabulary and produced a false positive on every single service booking.

### The destructuring that discards the error

Here is the highest leverage bug I found all year, and it is four characters wide.

The Supabase client does not throw. It returns an object with `data` and `error` fields. So this line, which I wrote dozens of times:

```ts
const { data } = await supabase.from('...').select()
```

discards the error **at the destructuring site**. There is no exception. The catch block never runs. `data` is null, the next line reads that as "nothing found yet", and the code carries on cheerfully doing the wrong thing.

There were roughly twenty four of those. One pattern, one afternoon of writing it without thinking, and it produced **every silent failure I found in a single week of review.** The worst instance: a missing table returned null, a check read that null as "no usage yet today", and a daily cap that I believed was enforcing itself was silently unlimited.

The type system was perfectly happy. The code compiled, passed review, and was wrong. A refusal that only exists in your head is not a refusal.

## The harness that refuses me

I built this with AI agents, and I want to be exact about what that means, because the useful part is not the part people usually write about.

I have written elsewhere about [what agents cost and where they fail](/blog/ubunye-series-part5-building-with-agent). This is a different argument. **An agent is a component. A component you cannot constrain is not a component.** So the work was not writing better prompts. It was building the surfaces that say no.

### The task file is a write scope contract

Every task in the queue is a file, and the header carries a field I now consider non negotiable:

```text
# TASK-031: Marketplace ranking
## Priority: HIGH | Phase: V3 | Depends on: none
## Files allowed: lib/ranking/calculate.ts,
                  app/api/admin/recalculate-rankings/route.ts
## Acceptance criteria
- [ ] calculateRankingScore() implements the scoring formula
- [ ] npm run build passes
- [ ] npm run test passes
```

`Files allowed` is handed to the agent before it starts. It is a declared blast radius, and it turns "do not modify files outside the current task" from a hopeful instruction into a checkable one.

What convinced me the format was real is how it degrades. Some tasks carry `Files allowed: (none, Supabase dashboard setting)`. The same field that scopes an agent is also how I mark work an agent cannot do at all.

### The same rule, enforced in three places

This is the piece I would take to any team.

| The check | For the agent | For CI | For me |
| --- | --- | --- | --- |
| No business values hardcoded in the app | A slash command that greps and reports | A job step that exits 1 | The constants file is an owned path |
| No provider SDK imported outside `lib/` | A slash command with per file exemptions | A job step that exits 1 | The provider directories are owned paths |
| No secrets committed | A slash command | A job step that exits 1 | Every env file is an owned path |

One rule, three enforcement points, aimed at three different things that can break it. The agent gets a command it can run before proposing a merge. The pipeline gets a step that fails the build regardless of who or what wrote the code. And I get a review request on the paths where somebody going off script is most expensive.

The rules were already in my project instructions before any of this. They were also already being broken. Writing them down is not enforcement.

### The command that refuses me, not the agent

The most useful thing in the harness is an autonomous command that decides what to build next. It reads the state, cross references what exists against the roadmap, and then walks a hard priority chain. The rule at the bottom is a prohibition:

> NEVER skip a priority level. Fix broken things before building new things.

It then writes a plan in a fixed template and stops, and waits for me to say go.

Read that again as a control system rather than as automation. **It refuses me.** Priority one is fix what is broken. Priority two is the landing page. New features are further down than I would ever naturally put them at eleven at night when a feature is the fun thing and the broken thing is not. The harness is a commitment device pointed at its author.

### Parallel agents, and the file count that dispatches them

Work is split by an unglamorous rule keyed on scope:

```text
under 3 files   ->  work solo, no teams
3 to 6 files    ->  research team + qa team
7 or more       ->  research + build + qa
references a
process doc     ->  always spawn research
```

When the build team runs, each agent gets its own git worktree so they cannot collide, and every worktree has to pass a build before it merges.

Six of those branches are still in my repository from 11 April. I went back and read them while writing this. Three agents, three vertical slices, disputes and suspension and the agent framework, with non overlapping file groups, migration files with adjacent timestamps, and not one conflict between them. The dispatch rule worked exactly as specified, which surprised me more than it should have.

### The review that argued itself into code

The best thing my agents produced was not code. It was an argument against something I was about to build.

I had wanted a panel of persona agents: a software engineer agent, a data scientist agent, a security agent. A structured adversarial review talked me out of it, and the reasoning is now a commit message I reread when I am tempted:

> A job title has no testable success predicate, so it cannot be evaluated or improved. Its scope overlaps every other title, so one stuck payout yields five opinions about one incident. The unit that works is the invariant: a property that must hold, owned by one deterministic check, with a precision you can measure and a mute you can pull.

So instead of personas I built a nightly consistency sweep. It calls **no model at all**, deliberately, and the file says why: a model asked whether the platform is healthy will answer healthy, because that is the modal output over log text.

The strongest check in it I named "money took, state did not move". The gateway confirmed a payment and the booking never advanced. It catches a webhook reconciling against the wrong total, a signature failure, a function timing out mid webhook, and any typo I introduce in that path in future.

Two rules govern what is allowed into that sweep, and both are in the source:

> Every one of these corresponds to a defect that was actually live in this codebase, which is the only reason it is here. An invariant nobody has ever violated is a guess.

and, on the tests:

> Roughly half of them are negative cases, proving the checks stay quiet on healthy but unusual data. A checker that never says nothing to do here is worse than none.

It found five live defects on its first real run. One of them meant that most of my notification system had been a silent no operation: fifteen of twenty three notification types were being rejected by a database constraint, so nobody was being told their gear was overdue, or what had happened to their deposit.

I also refused to call it self healing. The file says the honest name is **self observing**, and that anything which acts on findings comes later.

### Where the process broke

The queue is a directory of files, and a directory has no uniqueness constraint. Five task numbers currently exist in both the done folder and the todo folder. I did not notice for months.

The format degraded too. The early tasks are nine line contracts with acceptance criteria. By task forty two I had written a 971 line prose document, which is not a task, it is a wish. The recent ones snap back to the terse format, and one of them contains the sentence that is the whole thesis of this section applied to myself:

> It should not depend on somebody remembering.

And a correction I owe, since I nearly published the opposite. I had planned to write that my harness protects itself, because the ownership file guards my project instructions. It does. It also guards two files that no longer exist, and it still points at the old middleware path that a framework upgrade replaced, which means **the file doing my request validation is not covered by the tripwire meant to cover exactly that.** The tripwire drifted off the thing it was guarding and I did not notice for four months. That is the same failure as documentation drift, in the control system I built to prevent it.

Finally, the disclosure. In the two months of history my local clone can still traverse, sixty five of seventy six commits carry a co authorship trailer, and the eleven that do not are almost all merges. I cannot report the figure across all 257, because my local object store is corrupt and cannot walk past a certain commit. There is a task filed about that, in the same queue as everything else. This post was written the same way.

## Where the refusals are still fake

In the spirit of the thing.

**One AI endpoint is outside the control.** The spend ceiling and the usage tracking cover the agent runtime. An older chat route predates all of it, calls the model directly, and is therefore neither metered nor capped. Its guest limit also reads a count from the request body, which is to say from the caller. I found this while writing this post, which is a good argument for writing them.

**The consistency sweep only watches.** It notices, deduplicates and tells me once. Nothing acts.

**The dependency check is a moment, not a state.** I cleared twelve known vulnerabilities to zero in August. The check that would keep them cleared is still sitting in the todo folder, and two moderate findings have already appeared since. Nine of the original twelve had fixes available long before I looked, which is the actual lesson: nobody was looking.

**The ranking function has never been evaluated.** Its weights are asserted, not fitted, and I have never tested them against an alternative. That is fine at this volume and stops being fine the moment there is enough traffic to measure.

**One author.** Every abstraction in this post survives me leaving. The context does not.

## What I would take to another system

1. Put the rule where something can refuse it. A rule in a document is a wish, a rule in a grep that exits 1 is a control.
2. An alert is not a control. The email is a report. The gate that refuses the call is the thing.
3. Make unknown expensive. Unknown must never default to free, or to allowed, or to fine.
4. Write down why a thing is deliberately imprecise, or the next person will correct it into something slower and no safer.
5. Only write the check after the defect. An invariant nobody has ever violated is a guess, and a noisy sweep gets muted.
6. Constrain the agent by scope, not by instruction. Declared blast radius beats a polite request every time.
7. Point one of the constraints at yourself. The priority chain that refuses me is the most useful thing I built.
