# Network Architecture and Security: Where the Boundary Actually Is

*Deep dive five of six. Start at [the system map](/blog/thabangvision-system-design) for how this layer fits the rest.*

---

## The question this layer answers

Most application security writing assumes requests arrive through your code. On a modern hosted stack that assumption is false, and building on it produces a system that is carefully guarded along one path and completely open along another.

So the question here is narrow and it is the only one that matters: **which component is actually the last thing standing between an attacker and the data?**

For this system the answer is the database, not the application. Everything below follows from that.

---

## The request path

```text
   browser
      |
      v
  +---------------------------+
  |  edge interceptor          |
  |   - refresh session        |
  |   - validate origin        |  mutations only
  +------------+--------------+
               |
       +-------+--------+
       |                |
       v                v
  route handler     webhook route
   - authenticate    - verify signature
   - authorise         over the raw body
   - rate limit      - reconcile amount
       |                |
       +-------+--------+
               |
               v
        +--------------+
        |   database   |  row level security
        |              |  runs regardless of
        +--------------+  which path arrived
```

Three entry classes, three different trust models. A browser request carries a session and an origin. A webhook carries a signature and no session at all. And a direct database query carries neither, which is the case people forget.

### The interceptor

Session refresh and origin validation both live at the edge, before any route handler runs. That placement is the entire point: **a control in a shared interceptor cannot be forgotten by an individual route**, and a new route written at eleven at night inherits both automatically.

Origin validation applies to mutating requests only, and webhook paths are exempt because a server to server caller legitimately sends no origin header. Both variants of the site's own domain are accepted, because a user arriving without the subdomain prefix is a normal customer and not an attacker.

One deliberate choice worth naming: a request with **no** origin header passes. That is failing open, and it is a real trade. Some legitimate non browser clients send nothing. The second layer behind it is the session cookie policy, which prevents a foreign site from causing an authenticated request in the first place. Origin validation here is defence in depth rather than the primary control, and treating it as the primary control would be a mistake.

### Response headers as policy

Headers are set once and apply to every response. The set is ordinary: deny framing, block content type sniffing, restrict referrer information, enforce transport security, and a content security policy that names exactly which origins may supply scripts, styles, images, fonts, connections and frames.

Two details are more interesting than the list.

**Framing is denied twice**, once with the legacy header and once in the policy, because the two are understood by different browser generations and the cost of both is zero.

**Camera access is granted to the site's own origin, deliberately.** The default is to deny every device capability, and this one is an exception with a reason: identity verification captures a selfie in the browser. Microphone and location stay denied. That is what a permissions policy should look like, a default of no with individually argued exceptions, rather than a copied block nobody has read.

## The webhook trust chain

A payment webhook is the highest value unauthenticated endpoint in any commerce system. It carries no session, it arrives from outside, and acting on it moves money.

Three properties, in order.

**The signature is verified over the raw body, before parsing.** This ordering is not fussiness. A signature covers a sequence of bytes. If you parse first and verify against the reserialised object, you are verifying **your parser's output** rather than what the sender actually sent, and any disagreement between your serialisation and theirs is a gap. Read the body as text, verify, then parse.

**The comparison is constant time.** A byte by byte comparison that returns early leaks, through timing, how much of a candidate signature was correct. That is a slow attack and a real one, and the fix is a standard library call.

**The amount is reconciled before anything is confirmed.** A valid signature proves the message came from the gateway. It does not prove the message says what you expected. So the reported amount is checked against what was recorded at checkout, and a mismatch flags the booking for a human rather than confirming it. A verified message and a correct message are different claims.

There is also an ordering rule I got wrong once and would now treat as a principle. An early version validated a caller's address by string prefix rather than by proper network range arithmetic. A prefix comparison silently accepts a far wider range than the one intended, because address notation is not text. **An allowlist compared as strings is not an allowlist.**

Idempotency sits underneath all of it. A gateway will resend. The handler checks whether the work has already been done before doing it, in more than one place, because a duplicated payout is not recoverable by an apology.

## Row level security is the boundary

Here is the thing that took me longest to internalise about building on a hosted database.

The client key is **public by design**. It ships in the browser. Anyone who has loaded the site has it, along with the project URL. Which means every check written in an API route can be bypassed entirely by not using the API.

```text
   what a route diagram implies       what is actually reachable

   browser                            browser
      |                                  |     \
      v                                  v       \
   my route                           my route     \
      |                                  |           \
   authenticate                      authenticate     \
      |                                  |             |
      v                                  v             v
   database                           database  <--  direct query
                                                    with the public key
```

Route authentication is real and it protects the path through your code. **Row level security is the only thing protecting the data itself.** Everything else is a request to callers who have agreed to use the front door.

Three lessons from getting this wrong and tightening it, all of which generalise past any particular incident.

**Row level security is row level, so a column filter has to be a view.** There is no policy that says "this reader may see these columns". You create a view exposing only the safe columns and grant on the view. The formulation I settled on: **the view is the column filter, and the where clause is the row filter.** Two mechanisms, two jobs. Confusing them is how a column nobody meant to publish gets published.

**An update policy without a check clause is a privilege escalation.** A policy permitting a user to update their own row, with nothing constraining what they may set, permits that user to set their own role. The fix pins every field the user must not control to its current value. Read your update policies and ask what a user could **set**, not just which row they could reach.

**Write down why you deviated.** One view here is flagged by the platform's own linter, and is correct anyway, because it exists precisely to expose a safe column subset to anonymous readers and the alternative would mean opening the underlying table. That argument lives in a comment on the view itself. A deviation with a written justification is a design decision. The same deviation without one is a mistake nobody has caught yet.

### The revoke that reported success and did nothing

My favourite bug in this system, and it discloses nothing, so here it is in full.

Database functions are published over the REST interface. The linter reported that several of mine were callable without signing in. Each was guarded internally, so it was defence in depth rather than an open door, but a door should be locked rather than watched.

So I wrote a migration revoking execute permission from the anonymous and authenticated roles. It ran. It reported success.

Afterwards, out of habit rather than suspicion, I queried the actual privileges. Every function was still executable by anonymous callers.

Postgres grants execute on a new function to the `PUBLIC` role by default. The anonymous and authenticated roles both **inherit** from `PUBLIC`. Revoking a privilege from a role does not remove one that role inherits. My migration had revoked something those roles never held directly, and truthfully reported having done so, while changing nothing at all.

The second migration takes the grant from `PUBLIC` itself and hands it back only where genuinely needed. The line I put at the top of it is the most useful sentence I wrote all year:

> Checking the result rather than trusting success is what caught it.

**A statement that succeeded is not a statement that did what you meant.** That is the same failure as the silent error handling in the [software design deep dive](/blog/software-engineering-design), several layers down the stack, and I did not notice they were the same shape until I wrote both of these.

One function stayed anonymously callable, deliberately and with the reason recorded: many policies call it, policy expressions evaluate as the querying role, and revoking it would make the public catalogue fail to load. It only reports whether the caller is an admin, which the caller already knows. That written argument is what separates a design from a configuration.

## Rate limiting on a runtime that forgets

The first rate limiter kept counters in module scope. It looked correct and it was not a limit.

On a serverless platform each instance has its own module scope, and that scope dies when the instance is recycled. So a stated cap actually meant **that many requests per instance, until the instance is recycled.** Under concurrency the real ceiling was unbounded, and it reset constantly. That applied to the sensitive operations too: payouts, role changes, dispute resolution. Every one of those protections read stronger than it behaved.

The replacement is a single atomic statement in the database that inserts or increments and returns the new count, so two instances cannot both read a stale number and both conclude they are under the limit. Fixed windows rather than a sliding log, which permits at most twice the limit across a boundary. That trade is written into the migration rather than hidden, because twice the limit is a rounding error compared to no shared state at all.

Two details I would repeat.

**I renamed the function rather than changing it.** Moving the counter to the database made it asynchronous. Had I kept the name, every existing call site would have tested a promise for truthiness, which is always truthy, and **every rate limit in the application would have silently switched off while still type checking perfectly.** Renaming forced the compiler to point at every caller. When a change alters a function's contract rather than its behaviour, take the name away.

**It degrades rather than failing open or shut.** If the shared counter is unreachable it falls back to the per instance counter. A database problem narrows the limit instead of removing it.

### Denial of wallet

Any metered AI feature introduces an attack that does not exist in a normal application: the goal is not to take your data or your uptime, it is to **spend your money**.

The ingredients are always the same. An endpoint that costs money per call. A limit keyed on something the caller controls. And accounting that can undercount.

All three existed here at once. The guest limit was keyed on a forwarded address header taken whole, so varying it produced a fresh allowance every request. The cost estimate returned zero for any model not in the pricing table, so a misconfigured model recorded every call as free and blinded both the ceiling and the alert. And the ceiling itself did not exist yet, because the only guard was a daily email.

The fixes are individually boring and collectively the whole defence: take only the first hop of the forwarded address and treat a missing header as one shared bucket rather than an exemption, charge unknown models at the worst known rate, and put a real ceiling in front of the call. That last one is covered properly in the [AI engineering deep dive](/blog/ai-engineering-gateway).

The general principle: **if a request costs you money, rate limiting is a financial control and belongs in the threat model as one.**

## Deciding the failure direction on purpose

If you take one thing from this post, take this table. Four controls in the same codebase, each failing in a different direction, each direction argued at the time.

| Control | Fails how | Why that direction | What backs it up |
| --- | --- | --- | --- |
| Spend ceiling | Open | A database blip must not take the assistant down for every customer | Usage records and the daily report |
| Rate limiter | Degraded, not open | A loose limit beats no limit; locking everyone out beats neither | The per instance counter it falls back to |
| Origin validation | Open on a missing header | Legitimate non browser callers send none | Session cookie policy as the real control |
| Webhook signature | Shut | There is no legitimate caller without a valid signature, and the payload moves money | Nothing, and it should not need anything |

The reason this is the most senior object in the whole series: **there is no house style here.** Two fail open, one degrades, one fails shut, and each is right for its own blast radius. A codebase where every control fails the same way has not thought about any of them individually.

The method is two questions per control. What happens when this control itself is unavailable? And which is worse, the outage or the bypass? For a spend cap the outage is worse. For a signature check the bypass is worse. Writing the answer next to the code is what stops a future reader "fixing" a deliberate choice.

## What this layer buys

Security is not one of the four axes in this series. It is a precondition for all of them, because a system that loses its data does not get to have a conversation about efficiency. But the choices here do have axis effects worth naming.

| Decision | Effect |
| --- | --- |
| Controls in a shared interceptor | Scalability of the team, not the traffic. New routes inherit correctness. |
| Row level security as the boundary | Portability cost. These policies are the least portable part of the system and also the most important. |
| Shared rate limiting in the database | One database round trip per guarded request, paid deliberately for a limit that is real. |
| Tokenising banking data | Reduces breach impact, and reduces the compliance surface at the same time. |
| Failure direction chosen per control | Availability where an outage is worse, strictness where a bypass is worse. |
